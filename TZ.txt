🎯 Контекст и цель проекта

Необходимо разработать десктопное приложение на C++ (Qt 6), реализующее локальный RAG (Retrieval-Augmented Generation) пайплайн на основе готовой русскоязычной базы знаний.
Приложение должно использовать библиотеку FAISS для векторного поиска, SQLite (Qt SQL) для хранения текстов и взаимодействовать с LLM Llama через сетевые HTTP-запросы (Ollama / REST API).
 Цель этого учебного проекта - показать работу RAG - как он "подбирает" ответы и подсказки. Нужно будет испоользовать такие "техники"  как multy-query, Hybrid Search, rerank,...
 и отображать промежуточные результаты.
(левая часть основного экрана должна представлять чат с LLM, правая - отражать "шаги поиска", между левой и правой частями - поставить QSPliter).
 Oтдельным Tab-ом   сделать страницу настроек, где кроме URL (llama-сервера) можно будет представить список чек-боксов с использзуемыми на каждом прогоне "техниками RAG".

💻 Технологический стек и окружение

    ОС: Windows 10 (x64)
    Фреймворк: Qt 6 (компоненты: Core, Sql, Network, Widgets/Quick — UI добавлю сам)
    Система сборки: CMake
    Векторный движок: FAISS (C++ версия, подключение через CMake/vcpkg)
    Хранилище текстов: Встроенный драйвер QSQLITE (Qt SQL)
    LLM / Эмбеддинг-модель: Внешний сервер Llama (через REST API / Ollama), доступный по HTTP.

📐 Архитектура данных (Паттерн FAISS + SQLite)

Поскольку FAISS хранит только ID (числа) и векторы, необходимо реализовать гибридное хранилище:

    Векторный индекс FAISS (в RAM): Хранит пары [ID (int64_t) -> Вектор (std::vector<float>)]. Используется индекс faiss::IndexFlatL2 или faiss::IndexFlatIP.
    База данных SQLite (на диске): Содержит таблицу chunks. Структура таблицы:
        id (INTEGER PRIMARY KEY) — строго соответствует ID вектора в FAISS.
        question (TEXT) — исходный вопрос из датасета.
        context_text (TEXT) — готовый текстовый чанк на русском языке.
        answer (TEXT) — эталонный ответ.

⚙️ Функциональные требования к бэкенд-логике (C++)

1. Модуль работы с сетью (NetworkManager)

    Реализовать класс на базе QNetworkAccessManager для асинхронных HTTP POST-запросов к API Llama.
    Метод 1: Получение эмбеддинга. Принимает QString (текст), отправляет JSON-запрос к эндпоинту эмбеддингов (например, /api/embeddings в Ollama), возвращает вектор std::vector<float>.
    Метод 2: Генерация ответа (Chat/Generate). Принимает сформированный промпт (Промпт + найденный Контекст), отправляет запрос к модели Llama, возвращает текстовый ответ.

2. Модуль базы знаний (KnowledgeBaseManager)

    Инициализация: При первом запуске создает файл базы данных SQLite через QSqlDatabase::addDatabase("QSQLITE") и пустой индекс FAISS.
    Импорт данных: Реализовать парсинг скачанного файла базы знаний (формат .jsonl / JSON Lines). Для каждой строки:
        Текст q отправляется в NetworkManager для получения вектора.
        Вектор добавляется в индекс FAISS, библиотека возвращает его ID.
        Поля id, q, text (чанк) и a записываются в таблицу SQLite.
        (Опционально: предусмотреть сохранение/загрузку индекса FAISS на диск через faiss::write_index / faiss::read_index).

3. Пайплайн поиска и генерации (RAG Core)

Реализовать метод QString executeRAGQuery(const QString& userQuery), который выполняет следующие шаги последовательно:

    Вызывает NetworkManager для получения вектора вопроса пользователя.
    Передает этот вектор в метод поиска FAISS (index->search). Находит top_k (например, 1 или 3) наиболее похожих ID.
    По полученным ID делает SQL-запрос SELECT context_text FROM chunks WHERE id IN (...) через QSqlQuery.
    Формирует финальный промпт на русском языке, например:

    Контекст: [Тексты чанков из SQLite]
    Вопрос: [Вопрос пользователя]
    Исходя из предложенного контекста, кратко и профессионально ответь на вопрос.

    Отправляет промпт в Llama через HTTP и возвращает сгенерированный ответ.

🌐 Настройки API и Эндпоинты (Локальная Llama)

Все запросы отправляются локально на порт 8080.

    Базовый URL: http://localhost:8080
    Эндпоинт для эмбеддингов: POST http://localhost:8080/v1/embeddings (или /api/embeddings / /embedding в зависимости от точной сборки сервера).
    Эндпоинт для генерации текста: POST http://localhost:8080/v1/chat/completions (OpenAI-совместимый формат) или POST http://localhost:8080/completion      


При отправке запроса в Llama формируется JSON, где финальный текст (или массив messages) выглядит следующим образом:

Ты — строгое профессиональное ИИ-руководство для IT-специалистов. Твоя задача — отвечать на вопросы пользователя, используя ТОЛЬКО предоставленный ниже контекст.

🧩 Модуль нарезки текста (Text Chunking Engine на C++)

Поскольку используемый IT-датасет содержит длинные неструктурированные ответы, класс KnowledgeBaseManager должен включать в себя алгоритм Character/Token Splitting на базе регулярных выражений Qt (QRegularExpression) для автоматической нарезки текста на чанки.

Требования к алгоритму чанкинга (Реализует Cursor):

    Параметры нарезки (вынести в константы):
        CHUNK_SIZE = 600 символов (целевой размер одного текстового фрагмента).
        CHUNK_OVERLAP = 120 символов (перекрытие между соседними чанками, чтобы не терялся контекст на стыках).
    Логика разделения текста:
        Алгоритм не должен резать текст строго посередине слова или предложения.
        Разделение длинного текста ответа должно происходить по приоритетным границам в следующем порядке:
            Символ конца абзаца (\n\n или \n).
            Знаки окончания предложения (. , ! , ? ).
            Символ пробела (если предложение слишком длинное и превышает CHUNK_SIZE).
        Каждый сформированный чанк должен сохранять структуру: к тексту чанка автоматически приписывается мета-информация (например: "[Вопрос с Хабра: ... Раздел ответа: ...]"), чтобы векторная модель лучше понимала контекст.
    Связь с базой данных SQLite:
        После того как один длинный ответ с Хабра нарезается, например, на 4 чанка, каждый чанк получает свой уникальный ID в FAISS и записывается в SQLite как отдельная строка.
        У всех 4 чанков в SQLite должно быть дополнительное поле parent_id или source_question, чтобы приложение знало, из какого исходного треда взят этот кусок информации.
